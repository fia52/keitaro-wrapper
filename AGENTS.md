# Правила разработки keitaro-wrapper

## Архитектура

- Использовать чистую архитектуру: domain, application, infrastructure и presentation.
- Направлять зависимости внутрь: application зависит от domain; infrastructure и presentation используют контракты application и domain.
- Domain не зависит от FastAPI, SQLAlchemy, HTTP-клиентов или Keitaro API. Application не зависит от конкретных реализаций инфраструктуры.
- Размещать бизнес-правила в domain, сценарии использования и порты интеграций — в application, адаптеры Keitaro и SQLAlchemy — в infrastructure, HTTP-маршруты и схемы FastAPI — в presentation.
- Создавать и связывать конкретные реализации в отдельной точке сборки приложения. Передавать зависимости явно.
- Не выполнять запросы к Keitaro и базе данных непосредственно из HTTP-маршрутов. Не отдавать ORM-модели за границы инфраструктуры.

## Python

- Соблюдать PEP 8 и использовать автоматическое форматирование и проверку стиля.
- Типизировать все параметры, возвращаемые значения, атрибуты классов и переменные, включая локальные. Для None указывать явный тип, например `campaign_id: int | None = None`.
- По возможности использовать встроенные типы Python: `list`, `dict`, `tuple`, `set`, `str`, `int`, `bool`, объединения через `|`.
- В HTTP-слое использовать подходящие типы FastAPI. Не переносить их в domain или application.
- По возможности обходиться без модуля `typing`. Для абстрактных коллекций использовать `collections.abc`, для портов — `abc.ABC`. Импорт из `typing` допустим только при реальной необходимости, когда стандартных альтернатив недостаточно.
- Использовать одинарные кавычки для строк. Для docstring использовать тройные двойные кавычки согласно PEP 257.
- Снабжать каждый класс и каждую функцию, включая методы, коротким содержательным docstring на русском языке. Описывать назначение, существенные ограничения и побочные эффекты; не пересказывать код.
- Дополнительные комментарии писать там, где нужно объяснить причину решения или нетривиальное поведение.

## Интеграции и данные

- Хранить URL Keitaro, API-ключ и другие настройки в конфигурации окружения. Не добавлять секреты в Git, ответы API и логи.
- Изолировать детали Keitaro API в адаптере; передавать внутрь приложения собственные модели и ошибки.
- Управлять схемой базы данных через миграции Alembic.
- Не считать HTTP-вызовы Keitaro частью транзакции SQLAlchemy. Явно обрабатывать частичное создание кампании и сохранять идентификаторы созданных ресурсов для восстановления.
- Покрывать тестами бизнес-сценарии и существенные ошибки интеграции, включая частичные сбои. Использовать подмену Keitaro API в автоматических тестах.

## Объём работы

- Реализованы создание кампаний и редактор офферов существующих потоков. Редактор не создаёт и не удаляет сами потоки.
- Не добавлять функциональность за пределами согласованных требований без необходимости.
